## 2026-10-17 晚间：用户画像特征（F7）逐项裁决（Kiro，**Claude Opus 5.5**；逐项追加，全部裁完后才冻结）

### 第 1 项：anchor、对照与接入位置

1. **anchor = M1-mean**（序列用户塔，均值读出）。对照直接复用已验收的 M1-mean 三个 run（seed 42/2024/2025），不重训对照，与叠加实验同一做法。具体 run_id、manifest 与 config SHA 由 Codex 从 experiment_log 填进卡里，不凭记忆抄。
2. **重新审计重叠（Kiro 读 `04d4edeb` 的 `src/vkgr/retrieval_seqm1.py`）**：M1-mean 的用户向量是 `u = m + g·r`。
   - m 是 F4-T010 用户塔：对 H50 每个事件求“物品 embedding + 时长桶 T + 比例桶 R + 位置 P + 周间隔 G”，再取均值。
   - r 是一层 Transformer 分支，读的是**同一组**事件向量。
   - 事件侧只读时长、视频时长、周三个字段，**不读 like、place、platform**。
   - 所以草稿 §2 的重叠表对 M1-mean 仍然成立，但“平均观看比例”的重叠更强：r 可以对比例桶做非线性组合，重叠程度比对 F4-T010 时更高。like 率、场景/平台众数、H50 以外的累计规模，在 M1-mean 里都没有被读到。
3. **接入位置**：`u = m + g·r + p`。p 是画像各字段桶 embedding 之和（64 维），加在门控之外，m、r、g 的计算不改。
   - 画像表**全零初始化**，在全部共享参数按 M1-mean 同 seed 抽完之后再建；全零不消耗随机数。
   - 等价 oracle 只要求：初始化时 forward 输出与 M1-mean 同 seed **逐位相等**。不要求训练轨迹相等：画像表的梯度从第 1 步起非零，若训练用全局梯度裁剪，其它参数的更新也会随之不同。这是预期行为，不是 bug，卡里要写明。
   - 不加 MLP、user_id 表或交叉项（沿用草稿）。

### 第 2 项：窗口与字段（Eddy 选 Kiro 推荐方案 A，原话“按照你推荐的来试试”）

1. **U2 活跃度**：`N_exp`（累计曝光数，重复曝光保留）与 `N_like`（累计 like 数）。窗口为从可观察训练期起点开始的严格前缀，不截断。训练样本按 `(week, physical_row_ordinal)` 在每个 target 处先取快照、后更新当前事件；validation 只用第 00–24 周的固定快照。禁止用全训练期总量回填，也禁止用 `history_v2` 的切片统计或 H50 长度代替。
2. **U3 行为摘要只保留 H50 like 率**，与 M1-mean 读同一批事件，避免同时改变窗口。
3. **不纳入**：
   - H50 平均观看比例：与 M1-mean 的 m、r 两条路径都读的比例桶强重叠（第 1 项第 2 条）。
   - 场景 / 平台众数：FEAT-02 的 F5（逐事件加场景）seed42 只多 1 hit、判 inconclusive，压缩成众数的先验更弱。
   - 代价：这两个字段若其实有用，本轮测不出。
4. **事后调整的边界**：结果出来后，若要加回字段或换字段，属于新实验，需另起卡、由 Eddy 另批名额。不在本轮名额内按结果换字段。

### 第 3 项：分桶、缺失与边界（Eddy 同意 Kiro 推荐）

1. **U2 两个计数**：固定 log2 档位，不拟合。桶号 = 0（计数为 0），否则 `min(floor(log2 N) + 1, 16)`，每个字段共 17 档。两个字段各自一张 17×64 表。
2. **U3 H50 like 率**：`like 事件数 / H50 有效事件数`。
   - 档位：0 单独一档；大于 0 的部分按训练分位数切 8 档（7 个内部边界）；另有“H50 无有效事件、比例无定义”一档。共 10 档，一张 10×64 表。
   - 分位数只用训练样本在各自 target 处的快照值拟合，按样本计权；边界、拟合输入 hash、拟合脚本 SHA 记入 manifest。validation 只做 transform。若出现重复边界，按“去重后保留”处理并报告实际档数，不换方法。
3. **like 字段缺失**：冻结前由 Codex 在训练期做一次只读审计（缺失率、取值域）。缺失率为 0 则无需另定规则；不为 0 时，缺失事件从 like 率的分子和分母中都排除，`N_like` 只数明确的 like，`N_exp` 照常计数，报告写明比例。
   - 若 prepared / history 数据中**不含** like 字段、需要改数据合同才能拿到：STOP 回 Kiro，不自行扩展数据合同。
4. 不存在 OOV：计数和比例都有确定的档位。训练期没有记录的 validation 用户，U2 落 0 档，U3 落“无定义”档，如实统计人数。

### 第 4 项：实验臂、seed、名额与资源

1. 两个臂，各自单独对 M1-mean，不组合：**U2 臂**（N_exp + N_like）、**U3 臂**（H50 like 率）。
2. seed 42/2024/2025，三个无条件全跑，不做筛选；对照复用 M1-mean 同 seed 已验收 run。
3. **名额：2 个 P 线特征名额，共 6 个训练 + 6 个 verify，须 Eddy 批准**。批准记录写入本节之前，不入队任何科学训练。工程预演（preflight / CUDA / dry-run）不占名额。
4. 资源：新 CUDA 实测峰值 × 1.15 向上取整到 256 MiB，不沿用 M1 旧声明；驱动截止 48 小时。

### 第 5 项：判定表与转正条件（看结果前写死）

1. 每个臂按 §8.1 四行表判定（`D` = 三 seed Δhits 均值，`k₊` = Δ ≥ 6 的 seed 数，`p_pool` = 三 seed discordant 合并 exact 双侧二项），措辞沿用双向确认卡，对象换成“U2 臂 / U3 臂”与“M1-mean”。
2. **转正需同时满足**：§8.1 行 2；至少 2 个 seed 的逐 query exact McNemar p < 0.05；独立泄漏 review APPROVED；用户塔 model.users() 口径延迟报告（不称端到端）。条件与叠加实验相同。
3. 两个臂都转正时，本卡不选赢家、不自动合并，交 Kiro。
4. 机制描述（不参与判定）：按用户历史长度分档（H50 未满 / 已满）报告 Δhits。预期 U2 的增益若存在，应集中在历史超过 50 条的用户。
5. **已知风险（写进卡里）**：按近期批次估算，逐 seed p < 0.05 大约要求每个 seed 净多 27 hits 以上。画像特征的增益很可能小于这个量级，所以“方向为正但不转正”是一个现实的结果，不能据此改门槛。
