## 1. 三把尺子

| 名称 | 规则 | 用途 |
|---|---|---|
| 主尺子：长观看 | 整秒组内排前25%、阈值并列按 hash(user_id, item_id, 种子20261105) 补齐、排除dislike | 评估主结论；生成式与传统召回的默认训练目标 |
| 副尺子：有效观看 | 同上规则取前50% | 评估副报告；训练时低权重正样本 |
| like 尺子 | 原始 like 字段 | 与 varlen 等只用 like 的工作对比 |

- 分组：每个整秒 duration 一组，5–180 秒共 176 组；每组训练曝光 ≥169,557。
- 名额：floor(N/4)、floor(N/2)，N 为该组全部训练曝光（含 dislike 行）；dislike 行永不为正。
- 阈值：排除 dislike 后仍能凑满名额的最高整秒（离散分位，不插值）；14 组因此比插值分位低约 1 秒。逐组表：`cache/round4-2026-11/flat-calibrated/training_thresholds_and_hash_cutoffs.csv`。
- 查找表：176 行（主/副门槛、抽签比例、种子），只用训练周 week00–24 计算，冻结后应用到 validation 和 test。
- 稳定性：换种子 20261119，主尺子改标 6.919%、副尺子 1.317%；有模型后须用第二种子复核排名。
- 门槛统计误差：5–60 秒为 0；>90 秒主尺子约 ±2–3 秒、副尺子 ≤±1 秒（150 秒组用户块 bootstrap：主 [108,112]、副 [11,12]）。
- 训练端（待实验定，不挡路）：并列样本用软权重（= 组内抽签比例）而非 hash 0/1；副尺子权重；share/收藏加权。
- 不采纳任何绝对秒数下限，包括"看满视频时长与12秒中较小值"：它主要砍 10–15 秒短视频的正样本（9–16 个百分点），对 150 秒组零影响，公平度 1.19→1.60。证据：`docs/research/watch_threshold_and_duration_bands_2026-11.md`。

依据（原文）：DML（2306.17426）组内 P50/P75；D2Q 按时长分组去混杂；OneRec-V2 组内前四分之一、负反馈优先。精确名额与并列抽签是本项目自有构造，须在报告中声明。

## 2. 目标语义

- 定义为"累计偏好"：用户首次接触该视频后，数据窗口内累计观看达到同时长组分位。官方原文：timespent 累计所有观看、每 user-item 一行、行序按时间、uint8 封顶 255。
- 单次即时观看无法从数据构造，不作为选项。
- 已知局限（写一次即可，不停训练）：历史行 timespent 可能含预测时刻后的复看；累计窗口、更新时间、255 机制未知。

## 3. 适用范围

- 只适用 5–180 秒。完整目录 19,627,601 个视频全部在此范围（`cache/ur001-raw/metadata/items_metadata.parquet`）。
- 原因（原文）：VK Clips 上传 3–180 秒、<5 秒不进推荐；VK Habr 博客写明数据集 5–180 秒。见 `docs/research/vk_duration_policy_2026-11.md`。
- 180 秒组主门槛 84 秒偏低（179 秒组 103 秒，差 −19 秒 [−22,−17]）。原因是少数高曝光、观看短的视频：前 10 个视频占该组曝光 20.21%（179 秒组为 7.22%），其中 4 位作者在该组各只有 1 个视频，合计占 11.09% 曝光、门槛 20 秒。排除头部 10 位作者后，与 179 秒组只差 +3 秒 [0,7]。不改规则：180 秒组只占训练曝光的 0.05%。主目录和 Codex 分支 02dd 各跑了一次，核心数字逐项一致。

## 4. 评估规则

- 指标：封顶召回 = 命中数 ÷ min(K, 目标数)，在有目标用户上宏平均；K = 50/200/1000，主看 200。
- 置信区间：逐用户 bootstrap；模型比较用配对 bootstrap。
- 分档报告：主用 ≤60 / 61–120 / >120 秒；敏感性用训练曝光近三等分 ≤19 / 20–53 / >53 秒。分档结论须两种切法方向一致才成立。表中直接写秒数，不叫"短/中/长"。>120 秒档仅 4% 曝光，相对 CI 宽约 17%。
- 冷启动分开报：目标视频分"训练期见过 / 未见过"两组（validation 未见过占 26.5%），否则 ID 类与内容 SID 类模型不可比。
- 热度分层：后续按视频热度分头部/中部/长尾报告，并报候选覆盖率（细则待"多通路融合"讨论）。
- test（week26）只在最终读一次。

## 5. 其他反馈的用法

- share、收藏、打开评论区、进入作者页：评估时只做诊断（各尺子下的纯度与覆盖），不单独建尺子（验证周 share 9.8 万次、收藏 2.0 万次，过稀）。
- 训练时：优先作为**历史序列特征**（每个历史视频标注当时的反馈类型），其次作样本加权，多任务辅助头排最后。召回阶段不用 MMoE。
- 这些反馈只能放在历史视频上，不能放在被预测的视频上；视频级统计（如 like 率）必须按时间截断。

## 6d. 与 place 同类的问题（裁决者建议，待 Eddy 确认）

1. 历史行的反馈可能包含查询时刻之后的行为：timespent 官方写明累计所有观看；like 等布尔字段未写。可检验：若累计到数据窗口末尾，越早的周有越多时间累积复看，则"timespent 超过时长的比例""like 率"会随周号递减。交 Codex 按周画一张表即可，不改规则；主尺子验证周正样本率 25.27%、与训练名义 25% 接近，说明影响不大（推断）。
2. 目标的产生方式因 place 不同：place=0/1 约占验证周主目标 93%（由第八轮逐 place 表的曝光占比×正样本率估算），place=3/4/5 合计约 3%。后两类是用户自己点进作者页或搜索后出现的，推荐系统本来就推不到。固定 query 主报告也应加一栏按目标 place 分开的召回（至少分 place=0/1 与其他）。
3. geo 是"最常出现的地点"，聚合窗口可能含验证周和测试周；item 侧 train_interactions_rank 和内容向量的 SVD 窗口同理未知。处理不变：使用并披露。
4. 历史行的 click_on_author=1 之后常接着出现同作者的 place=3 曝光，这是合法的历史信号，不算泄漏。

## 6i. 第十五轮内容向量工业实践：裁决者审批意见（2026-11-07）

报告：Codex 分支 02dd 的 `docs/research/content_embedding_practice_2026-11.md`，证据在 `cache/round15-content/`，新增 16 份笔记。报告里提到"结论页 SHA 并发变化"，那是裁决者同期在写第 9 节，不是异常。

**批准**，按以下几点修正第 9 节的物品塔：
1. **ID 遮挡的准确说法。** DropoutNet 原文是把整条协同输入置零、保留内容，用老模型的打分作监督，遮挡率 0.5。我们沿用"整条 ID 分支置零"的做法，但监督仍用观看 retrieval loss。所以对外称"借鉴 DropoutNet 的输入缺失训练"，不称复现。遮挡率先比较 0.3 和 0.5。
2. **CLCRec 是离我们最近的参照**：同样是 64 维预提取特征，也做了内容与协同的对比对齐。它的 warm/cold R@10 是 0.0238/0.0313，同表 DropoutNet 只有 0.0102/0.0010。据此在物品塔加一项可选的辅助对齐损失：只走内容的向量要靠近同一视频的完整向量。列入第二批。
3. **内容被 ID 压制**（Pinterest Warmer）：要单独监控"只走内容"那条路径的召回，作为必报诊断。
4. **结构上限**：内容、作者、时长都相同的视频，只走内容时必然得到同一个向量。召回时它们打分并列，按评估框架的固定 hash 规则排先后，并报告这类并列占比。
5. **不做白化**：官方 SVD 分量本来就按信息量排序，强行把各维方差拉齐，可能放大低信息量维度里的噪声。
6. **打分方式**：物品塔对全目录逐个算向量后再检索，不用"固定的 ID 分类头"，这样新视频始终可以被打分。对比 M2TRec 的教训：它输入里虽然没有 ID，但输出仍依赖 ID 分类头。
7. **可学习的码向量**（QARM，以及 Google 的 Better Generalization with Semantic IDs）和第 9 节的"SID 前缀向量"是同一个方向，等 SID 码本建好后再做。

## 6j. 官方物品热度排名探针：裁决（2026-11-07）

报告：Codex 分支 02dd 的 `docs/research/item_rank_probe_2026-11.md`，证据在 `cache/item-rank-probe/`，核验 27 项通过。

**证据**
- 本地训练期零曝光、在 week25 最热的前 100 个视频，官方 rank 全部落在末 10%。
- 这组视频中 week25 曝光不少于 100 次的有 7,243 个，rank 与 week25 曝光数的 Spearman 只有 0.0040。
- 训练期零曝光、但 week25 出现过的 327,717 个视频，没有一个进入官方前 10%。

如果 rank 混进了 week25 的数据，这些"week25 才火起来"的视频应该排在前面。实际上它们全在末尾。

**裁决：证据足以接受该字段只用了训练期，但用法要受限。**

**一个新发现，比泄漏风险更要紧**
- 官方末尾大约 10% 基本就是"全量用户在训练期也没看过"的视频，可以看作真正的新视频。
- 训练数据里的正样本几乎不会来自这一段：训练期有曝光的视频落在末 10% 的比例不超过 0.15%。
- 后果：如果把 rank 直接喂给物品塔，模型很可能学成"排名在末尾就不推荐"，验证周的新视频会被系统性压低。这和"视频统计特征压制新视频"是同一个问题，而且更严重。

**用法**
1. **细分冷启动报告。** 把"训练期未见"目标再拆成两层：
   - 全量也未见：rank 落在末尾区间，算真正的新视频；
   - 仅本地未见：其他 99% 的用户看过。

   末尾区间的边界由 Codex 按分布拐点提出。这一层拆分直接服务于研究主问题。
2. **当物品塔特征时，与 ID 一起遮。** 末尾区间统一记为"未知"。训练时，被遮掉 ID 的视频，rank 也一起改成"未知"。必须做"加 rank / 不加 rank"的消融，并分层报告新视频的召回。
3. **新增第五条不训练基线：** 按官方 rank 排的全局热门，走统一评估框架，分层报告。

**具体规则（2026-11-07 补充，回答 Eddy 追问）**
- **分界怎么找。** 本地训练期出现过的视频，全站至少被看过一次。如果官方 rank 按全站训练交互数排序，这些视频必然都排在"全站零交互"的视频前面。所以分界取"本地训练期见过的视频里，rank 最大的那个值"。为防个别异常值，也可以取 99.99 分位，由 Codex 实测：统计末尾 15% 里每个 rank 区间有多少本地见过的视频，降到 0 的位置就是分界。
- **新视频怎么拆成两类。** 验证周的未见目标里：
  - rank 在分界之后的，算"全站新视频"；
  - rank 在分界之前的，算"仅本地未见"。
- **特征怎么取。**
  - rank 在分界之前：取 log(rank+1)，等频切成约 20 个桶，查表得到向量；
  - rank 在分界之后：统一记为"未知"桶。全站零交互的视频之间，rank 先后没有信息。
- **训练时的遮挡。** 被随机遮掉 ID 的视频（初值 30%），rank 也一并改成"未知"。这样"未知"桶在训练里见过大量正样本，不会被学成"不推荐"。
- **全目录三分组（Eddy 问，2026-11-07）**：19,627,601 个视频都可以分成三组：
  - 本地训练期见过：约 1,201 万；
  - 仅本地未见：rank 在分界之前；
  - 全站新视频：rank 在分界之后。

  依据是"本地见过的视频必然在全站被看过"这层包含关系，加上"rank 按全站训练交互数排序"这一推断（数据卡称其为 popularity rank，第八轮和探针的统计都支持）。分组只用于报告分层，**不作为模型特征**：训练正样本按定义全部属于第一组，把组别喂给模型只会教出"非第一组就不推荐"。真正进入物品塔的是 rank 桶，以及末尾的"未知"桶。
- **细分诊断（Eddy 2026-11-07 确认：先这样做，看效果）**：主报告固定按三组；每组内部再按一个维度切开，只做诊断：
  - 本地见过：按 6g 第 8 条的热度分层，分头部、中部、长尾；
  - 仅本地未见：按官方 rank 分成高、中、低三档；
  - 仅本地未见和全站新视频：再按"作者在本地训练期是否出现过"切开，用来检验作者向量和作者统计能不能给新视频搭桥。
  - 先例：见过 / 未见的 warm/cold 两分是通用做法，如 DropoutNet、CLCRec、LIGER；Temporal reachability（2607.21101）还按 token 支持情况细分未见目标。"用户抽样 + 全站目录"导致的"仅本地未见 / 全站新"两分，裁决者没见过专门的先例，交 Codex 核实。若确实没有，可以作为本项目自己的设计点来讲。
- **评估要求。** 必须报告：分界值和两类目标的数量；加 rank 与不加 rank 的召回，按"见过 / 仅本地未见 / 全站新视频"三层分开。

**剩余不确定性**
- week26 无法检验（不能读测试周）；

- 正确的目标是：一个 batch 里不同用户要多，同一用户的目标要少。

1. 只用均值结构（每个 epoch 约 22 分钟），同批 2,000 用户，seed 42，各训 1 个 epoch。每用户每步上限取 64、8、1 三档（1 档基本等于旧的随机抽样），看召回能否回到旧水平。

3. 如果上限必须很小才能恢复、速度又掉得太多，就改用跨 batch 负样本缓存（Cross-Batch Negative Sampling，Wang et al., SIGIR 2021）：前几步的物品向量留作额外负样本，用户侧仍共享计算。

1. **主线不变**：仍是全目标随机 shuffle、batch 1,024（6p 第 1 条）。

## 6t. 第二十三轮 batch 组装与负样本整理：裁决者审批意见（2026-11-09）

报告：主目录 `docs/research/batch_negatives_survey_2026-11.md`，证据在 `cache/round23-batch-negatives/`。核对了 `hypothesis_outcome.json` 和事前规则文件，数字一致。没有训练、没有推理、没有读第 26 周。

**一、顺序假设**

统计：
- 按训练目标数把用户三等分。最轻档（训练目标 ≤641）贡献了"按顺序减打乱顺序"增量的 61.3%，区间 [28.8%, 79.6%]，包含 50%；中间档贡献 32.6%，最重档 6.1%。
- 最轻档的召回：按顺序 5.38%，旧随机 5.31%，打乱顺序 3.99%（打乱顺序比旧随机低 −1.32 个百分点，区间不含 0）。中间档按顺序比旧随机高 +0.55 个百分点，区间不含 0。
- 末次训练位置：按顺序三档的中位数都在 99.95%；打乱顺序的最轻档是 96.9%。两者的配对中位差是 3.06 个百分点，没有达到 10 个百分点的门槛。
- 事后描述：按顺序时，最轻档用户平均 80.5% 的训练目标落在最后 10% 的更新里，打乱顺序时只有 10.7%。

裁决：
1. **10 个百分点的门槛本身不离谱，问题出在指标选错了。** "最后一个目标的位置"是最大值统计量。只要一个用户的几百个目标是随机散开的，他的最后一个目标几乎必然落在 epoch 的最后几个百分点（n 个均匀点的最大值，期望约为 n/(n+1)）。所以这个指标的天花板很低，任何"差 10 个百分点"的门槛都几乎不可能达到。判据措辞是裁决者在第二十三轮指令里写的，责任在裁决者；Codex 在设门槛前，没有先估一下这个指标在随机情况下的取值范围，下次补上。
2. 按事前规则，结论记为"不支持，方向一致"，不改写。裁决者的综合判断是**"方向支持，机制未证实"**：轻度用户的目标确实集中在 epoch 末尾（80% 对 11%），增量也主要来自较轻的两档。但份额区间包含 50%，只有单 seed，而且中间档的增益也不小，dropout 随机流的变化等其他解释都排除不了。
3. **到此为止，不再为顺序问题投入。** 对决策没有影响：主线仍是随机 shuffle，按顺序组装仍只是提速备选（6s 第 2、3 条）。如果以后真的启用它，必须补多 seed，并按活跃度档分别报告召回。
4. 新增的固定要求：以后所有组装或负样本对照，都要附上按训练活跃度三档的召回（复用本轮的分档脚本）。原因是用户等权的宏平均，对轻度用户特别敏感。

**二、现有 loss 核对**

- 两个用户同时以同一个视频为目标时，已经互相屏蔽，不会成为对方的负样本，相当于 TFRS 的 RemoveAccidentalHits。
- 同一个视频作为第三人的负样本可以重复出现，不做去重。这和"按出现频率有放回采样、频率取对数修正"的标准 logQ 口径一致，不改。
- Q 按出现次数计，不按 1 / 0.25 的权重计，是对的，因为采样概率只和出现次数有关。
- logQ 对正样本那一列也扣，这是 Yi 等 2019 的标准写法。2025 年 corrected logQ 认为正样本那一列不该扣，这一点列为下一轮的候选对照。
- "没有可用负样本的行，loss 为零，但仍然执行 optimizer.step"：随机 shuffle 下基本不会出现，只记录，不改。
- 训练中从没当过目标的视频永远不当负样本，已证实。混合负采样是对症的解法，列为下一轮候选。

**三、文献与后续**

- 接受这份文献表作为负样本部分的参考底稿。
- 第 9 节写的"不加均匀负样本（旧实验无增益）"，当时只看了整体召回，没有单独看冷路径和全站新视频这两组，所以重新开放，作为下一轮候选。

- 梯度投影维持备用。
- Nash-MTL 的许可没有确认，不复制它的代码。

## 6u. 第二十四轮负样本两组对照：裁决者审批意见（2026-11-09）

报告：主目录 `docs/research/negatives_contrast_2026-11.md`，证据在 `cache/round24-negatives/`。数字已和 `paired_differences.json` 对上。条件：均值结构、随机 shuffle、单 seed、各跑 1 个 epoch。

统计（相对基线的配对差，单位：百分点）：

| 范围 | 修正版 logQ | 混合负采样 |
|---|---|---|
| 整体 | +0.05 [−0.25, +0.32] | −0.05 [−0.43, +0.30] |
| 冷路径 | −0.04 | **+0.57** [+0.25, +0.87] |
| 本地见过 | −0.06 | **+0.39** [+0.02, +0.75] |

| 全站新代理 | +0.19 [−0.04, +0.39] | **−0.97** [−1.37, −0.60] |
| 中间活跃度档 | +0.30 [+0.03, +0.62] | +0.43 [+0.04, +0.83] |

速度：两组都从 1,069 降到约 580 目标/秒。

1. **混合负采样学到了"缺特征就压低"的捷径**（代码已核对，机制是假设）。
   - `Catalog` 里训练次数不够的视频，ID 序号是 0（padding，零向量）；作者从没出现在训练目标里的，作者序号也是 0。全站新视频和仅本地未见的视频，大多同时缺 ID 和作者。
   - 均匀负样本里约四成是这类视频，而它们从不当正样本。模型很容易学会"没有 ID、没有作者的就打低分"，于是新视频被成片压下去。
   - 已知视频的竞争者变少了，所以本地见过的视频和冷路径（候选都置零 ID，但保留作者）的召回反而上升。
   - **这不只是代理口径的假象**：真正上线后的新视频同样缺 ID、常常也缺作者，会被同样压低。
2. 修正版 logQ 没有显著变化，全站新代理的区间刚好压在 0 上。速度减半主要来自 float64 和新增的 mask 计算，不是方法本身的代价。

裁决：
1. **混合负采样不采用**。全站新视频召回是本项目的核心卖点，不能用它去换冷路径和已知视频的召回。第 9 节"不加均匀负样本"恢复有效，理由改为本条。以后如果要扩大负样本池，必须先避开"缺特征"这个可被识别的模式（例如只从有 ID 的视频里抽，或者对作者也做 dropout），而且要以全站新视频召回不下降为硬条件。目前不排期。
2. **修正版 logQ 不作默认**，保留为可选开关。上服务器全量训练时，如果预算允许，作为一组对照（要先改回 float32）。
3. **双塔负样本这条线在本地子集上到此结束**。第十八到二十四轮已经覆盖了组装方式、顺序和负样本三个方面，主线保持第十八轮的口径：随机 shuffle、batch 1,024、标准 logQ。

1. **热度排序对新视频比随机还差**（65.4% 对 71.4%），印证了"热度让新视频沉底"的担心。它只对已见过的视频最好。

4. TIGER 式的"加一位区分 token"对新视频基本学不到：新视频从没在训练里出现过，生成器无从学会它的第 4 位，所以近似于随机挑选（约 71%），比双塔打分（81%）差。GRID 的实验里，加位和随机挑选也只差一点。这一条是推断，没有实测。
5. 成本：SID 本来就用物品塔的冷路径向量来切码，用户 query 也是现成的，按双塔打分只是多做一次几百维的点积，基本不增加成本。

3. 展开后整份候选按双塔分重排（LIGER 式的稠密重排），放到问题 4、问题 5 里和 beam 宽度、候选预算一起讨论。

## 6w. 第二十六轮码内排序 λ 扫描：裁决者审批意见（2026-11-09，λ 初值待 Eddy 确认）

报告：主目录 `docs/research/sid_within_code_order_followup_2026-11.md`，证据和图在 `cache/round26-sid-order/`（`pareto_frontier_final.png`）。λ = 0 时与第二十五轮逐目标完全一致，已核对 `pareto_points.csv`。

统计（每个码只取第 1 名，前提是生成器已经猜对完整码；排序分 = 双塔余弦 + λ × ln(训练目标次数 + 1)）：

| λ | 本地见过 | 全站新代理 | 全部目标 |
|---|---|---|---|
| 0 | 81.7% | 81.4% | 81.6% |
| 0.01 | 84.6% | 80.3% | 83.6% |
| 0.02 | 86.6% | 79.5% | 85.0% |
| 0.05 | 90.2% | 77.5% | 87.3% |
| 0.1 | 92.2% | 75.1% | 88.3% |
| 0.2 | 92.7% | 72.8% | 88.2% |
| ≥ 0.3，直到纯热度主序 | 92.7% → 91.9% | 71.9% → 70.4% | 下降 |

推断：
1. λ ≥ 0.3（含纯热度）全部被支配：两组都不如 λ = 0.2。**纯热度排序在任何偏好下都不是最优。**
2. 前沿的拐点大约在 λ = 0.05。从 0 到 0.05，老视频每多保住约 2.2 个点，新视频只丢 1 个点；从 0.05 到 0.1，老视频只多 2 个点，新视频却丢 2.4 个点，开始亏本。
3. λ 的数值只适用于当前的冒烟权重。正式双塔训练后，余弦分数的分布会变，同一个 λ 的含义也会变，所以**这里定的是规则形式和选点方法，λ 的具体数值以后要重扫**。
4. 文献补充：Spotify 线上就用"同码按热度挑一条"，相当于这里 λ 很大的一端，说明我们的前沿给出了更好的折中。Gryphon（2026）让生成器自带物品级打分头，属于问题 4 的候选结构。ZCR（2026）在每个前缀下按量化误差重新分配末层码，做到零碰撞，列为切码阶段的候选，等有生成器以后再比。末位 token 那篇只核到 README，不引用结论。

裁决：
1. **码内排序规则定为"双塔分 + λ × ln(热度 + 1)"**。纯热度排序只作对照，不再作为候选。
2. **λ 的初值定为 0.02（Eddy 2026-11-09 确认）**：裁决者建议 0.02，也就是新视频最多丢约 2 个点。理由：新视频召回是本项目的卖点，按 6t 的规则，容忍度由 Eddy 给。备选 0.05（拐点），或者 0（完全不加热度）。
3. 正式双塔和生成器训练出来以后，在**最终召回@200**上重扫 λ，再画一次前沿（并入第 7 节第 3 条的融合寻参）。这里的"码内保留率"只是条件统计，不当最终依据。
4. 问题 3 到此结束，下一步讲问题 4（生成器结构）。Gryphon 的物品打分头作为问题 4 的讨论材料之一。
5. 补充（2026-11-09，回答 Eddy"λ 以后要改，初值是不是随便设"）：λ 只作用在生成器输出之后的码内排序，改它不需要重训任何模型，所以以后重扫基本免费。初值也不是完全随便：问题 4 里各种生成器结构的对比都会带上码内排序，要固定用同一个 λ，而且要落在前沿上（不能落进 ≥ 0.3 的被支配区）。在 0–0.05 之间选哪个，对各方案之间的相对比较影响很小。
6. 问题 3 的边界：**规则形式和选点方法已定，不阻塞问题 4**。留到正式训练以后的有三件，都已记在别处：λ 在最终召回@200 上重扫（本节第 3 条）；正式物品塔导出、按第 8 节问题 1 换成冷路径向量重新切码以后，复核码下视频数和本轮保留率（本轮用的是官方内容向量切码、冒烟权重打分）；ZCR 零碰撞切码作为另一条路，等有生成器以后再比（第 4 条）。

## 6x. SID 问题 4 第一点：历史怎么输入（2026-11-09，Eddy 已确认）

依据：第二十一轮调研（主目录 `docs/research/generator_survey_2026-11.md`）和合同里"最近 200 条全部 place 曝光"的口径。

决定：用多个方案对比，找最优，不预先只押一种。
1. **主线：事件 token**。每条历史占 1 个位置，向量由三部分合成：3 位 SID 的 embedding（让输入和输出用同一套码）、冷路径内容向量、该条历史的反馈 / 观看时长 / 场景。先例：OneRec 技术报告 §2.2.1。
2. **对照一：TIGER 式 SID token**。每条历史展开成 3 个 SID token，200 条历史共 600 个位置，不带反馈。
3. **对照二：事件 token 去掉反馈**。用来分清主线的提升来自"长度变短、带内容向量"，还是来自"反馈"，避免把结构变化和特征变化混在一个对照里（第二十一轮报告的提醒）。

理由：
- 我们的历史是曝光序列，既有点赞看完，也有很快划走；只写 SID 的话，两者在输入里完全一样。TIGER 的历史是写过评论的商品，本来就全是正样本，所以不受这个问题影响。
- 位置数是 200 对 600，全注意力的计算量大约差 9 倍。
- 约 25% 的新视频和见过的视频共用完整码（6q），只写 SID 的话，历史里这些视频分不清。
- 历史里出现新视频不是区分点：全站视频都有 SID 和冷路径向量，两种写法都能输入。

还没定：具体的合成方式（拼接后过 MLP，还是相加），跟问题 4 后面两点一起看。HSTU 式的"物品、动作交错"（每条历史 2 个位置）是第三种写法，下一轮定向调研时一起核。

## 8. SID 初始方案（第九轮，裁决者建议，待 Eddy 确认）

**问题 1 已定（Eddy 2026-11-08）：** SID 的输入向量改为训练好的双塔物品塔冷启动路径的输出（只用内容、作者、时长，ID 置零），官方内容向量作对照组。下面"推理时只用内容作入口（官方 64 维向量）"一条由此替换，原文保留。代价：SID 要排在双塔之后，物品塔每改一版都要重新切码。先例：QARM、OneRec TR、PLUM、LETTER 都是"用行为信号训练内容表示，再量化"；直接复用召回双塔的冷启动路径作切码输入，第九轮的资料里没找到完全一致的做法，不作为方法创新来宣称。

补充（2026-11-09）：第二十一轮找到直接先例。COINS §2.2 原文写明"训练双塔召回模型，取物品向量做 RQ-KMeans"。带 ID dropout 的冷路径这一点，在所查来源里没找到完全相同的做法，见 6r。

报告：主目录 `docs/research/sid_survey_2026-11.md`，证据在 `cache/round9-sid/`。

**可以定为规则的部分：**
- 推理时只用内容作入口（官方 64 维向量，逐条做 L2 归一化）。这样训练期没见过的视频也能编码。
- 码本只用训练期见过的视频拟合，冻结后给全部 19,627,601 个视频编码；内容 encoder、码本、SID→视频映射、前缀树、生成器分别记版本。
- 允许多个视频共用一个完整码。评估时先按码展开成真实视频列表，在码内排序、过滤历史并去重，再截到 K；按视频级算召回，CCE 只作诊断。
- 用全目录合法前缀约束解码；beam 宽度、展开出的候选数、最终视频数分开报告。
- 训练见过的目标和训练没见过的目标始终分开报告。

**需要实验定的参数：**
- 码长与码本大小：起点用 3 层×1024（未见目标所在桶 P99 为 23 个视频，与见过的视频共用完整码的比例为 27.93%）；4 层×256、3 层×4096 作对照。
- 协同对齐的具体做法（QARM、OneRec TR、PLUM、LETTER 这类"训练时用协同监督、推理只用内容"的路线）：对齐网络、配对来源、损失权重。
- RQ-KMeans 是否换成平衡分配或 RQ-VAE；拟合样本要从 20 万扩大，并做多次初始化；beam 宽度；码内排序方式。
  - 补充（2026-11-09）：码内排序方式已定，见 6w——"双塔分 + λ × ln(训练目标次数 + 1)"，λ 初值 0.02，正式训练后在最终召回@200 上重扫。

**关键证据：** 不训练的内容均值基线在全目录上的封顶召回@200 只有 0.157%，低于"按训练末作者推热门视频"基线的 0.611%（两者都是全目录、训练末固定 query）。在共同的旧目录上，旧 SGNS 协同向量召回是内容向量的约 2.5 倍。所以协同对齐是生成式线的核心，不是可选增强。另外，有完全相同的内容向量（最大桶 973 个视频只有 200 种不同向量），只靠内容无法把它们区分开。

## 9. 双塔初始方案（2026-11-07，Eddy 确认开始实现；数值参数为初值）

旧双塔的配方和消融结果见主目录 `docs/presentation/2026-10-19-complete-project-review.md` 第 160–205 行。旧口径是 like 目标、历史 50 条、目录 12 万、2,520 条验证，下面的旧结论只当方向参考。

1. **物品塔**
   - 视频向量 = 内容投影（64 维内容向量经 MLP）+ ID 向量 + 作者向量 + 时长桶。
   - 新视频没有 ID 向量，只走内容、作者和时长这几路。作者也没见过时，作者一路同样为空。
   - 训练时按比例随机遮掉 ID（DropoutNet 思路，遮挡率初值 0.3，待实验），逼内容一路自己也能给出好向量。
   - ID 表只给训练曝光不少于某个阈值的视频，阈值由 Codex 按显存和覆盖率实测后提出。
   - 旧实验"作者和内容放两侧"是 −37，但当时只评见过的视频。所以作者向量做一次去掉它的消融。
2. **用户塔**
   - 沿用旧的最好结构：历史均值，加一个门控的 causal Transformer 残差。
   - 每条历史事件的输入：共享的物品向量、九个反馈位、观看比例桶、place、位置、周间隔。
   - 新近性加权（旧实验 τ=0.10 有效但没转正）作为消融。
   - 不用多兴趣（旧实验 −25 到 −34），不加用户画像（旧实验 0 到 +7）。
3. **损失与负样本**
   - cosine 加温度 0.10（旧实验在 0.05/0.07/0.10/0.25 里最好），维度 64。
   - batch 内 softmax，减 logQ，频率用训练目标的出现次数。
   - 屏蔽 batch 里属于该用户训练期正样本的列。
   - 不加均匀负样本（旧实验无增益）。2026-11-09 更正：旧实验只看了整体召回，6t 将其重新开放为下一轮候选。第二十四轮复测后，不加均匀负样本的结论恢复有效，理由改为它会压低全站新视频（见 6u）。
   - batch 在少量用户上比较 1,024 / 4,096 / 16,384 三档。
4. **训练样本**
   - 每个目标位置一条样本，历史取它严格之前的最近 200 条曝光。
   - 目标是 place 0/1 的主尺子正样本，权重 1；只满足副尺子的，权重 0.25。
   - 默认按目标自然分布采样（旧实验按用户平衡采样有害），每人最多 64 个作为对照。
   - 工程上允许用 causal 结构一次算出一个用户的所有目标位置，等价于逐条计算即可。
5. **推荐与评估**
   - 训练末用最近 200 条训练曝光算出用户向量，在全目录 1,962 万个视频里取前 1000 个，交给第十三轮的统一评估框架。
   - 全目录检索可以用 FAISS 近似检索，但要用精确检索抽样核对重合率。
6. **候选统计特征**：旧实验中"候选热度 / 新鲜度 / 观看质量 + 行为权重"组合有 +45 到 +68。放到第二批实验，主线先不加。Eddy 提议（2026-11-07）在同一批里加"受众统计"：用训练周数据统计每个视频观众的年龄、性别、地域分布和平均观看比例，作为物品塔的显式特征。这类统计只有训练期见过的视频才有，新视频为空，所以遮 ID 时要同时遮掉它。Eddy 进一步提议（2026-11-07）用"物品侧行为序列"：取每个视频最近若干个长看用户，把这些用户的表示聚合进物品向量，让物品塔显式带上"谁爱看它"。业界同类做法有图模型聚合邻居用户（PinSage、LightGCN）、CTR 里的物品侧用户序列（如 DUMN）、双塔信息互通（如 Meituan 的 Dual Augmented Two-Tower），具体细节交 Codex 核实。注意三点：
- 训练时必须把"当前这条样本的用户本人"从该视频的用户列表里剔除，否则等于把答案写进了题目；
- 只能用训练周的数据；
- 对训练期零曝光的新视频，这个列表是空的，帮不上忙，主要帮助曝光很少的长尾视频。
列为第三批实验候选。

物品塔完整输入清单（2026-11-07 汇总）：
- 原始元数据只有四列：`item_id`、`author_id`、`duration`、`train_interactions_rank`（已定不用），另有 64 维内容向量。其余都从训练周交互里统计出来。
- 主线：内容向量（MLP）、作者向量、时长桶、ID 向量（遮挡）。
- 第二批：
  - 视频统计：热度、新鲜度、观看质量（平均观看比例、主尺子正样本率、秒划率、like 率）、受众统计、场景分布；
  - 作者统计：作者热度、作者的平均观看质量、作者的受众统计。
- 第三批：物品侧用户序列。
- 风险：新视频的视频统计全是空或 0，模型可能学成"没统计就是冷门"，反而压低新视频。所以视频统计必须和 ID 一起遮。作者统计对"老作者的新视频"有效，是给新视频搭的一座桥，不随 ID 一起遮。
- 待第十三轮实测：验证周未见目标里，作者在训练期出现过的比例。
- 物品塔内部结构（2026-11-07，Eddy 问）：主线用"各路相加 + 两层 MLP"。可比较的升级候选：
  - 特征交叉层，如 DCN-v2；
  - 把每个输入当作一个 token、做 1–2 层 self-attention，如 AutoInt 的做法；
  - 图或邻居聚合，与第三批的物品侧序列合并考虑；
  - 不只用点积的相似度，如 Meta 的 mixture-of-logits。
  这些具体出处和效果交 Codex 核实。物品只有几个输入、不是序列，预期结构升级的收益小于特征和训练方式，所以排在特征批次之后。
- 澄清：FAISS 只用于双塔的稠密向量。生成式那条线是 beam search 走 SID 前缀树，不经过 FAISS。SID 进入双塔时，只作为物品塔的输入特征，也就是 SID 前缀向量。
- 补充候选（2026-11-07）：
  - 官方物品热度排名：先做泄漏探针，见 6g 更正。
  - SID 前缀向量：参考 Google/YouTube 的"Better Generalization with Semantic IDs"（2306.08121），用 SID 前缀的向量让相似视频共享参数，新视频也能用。待 SID 码本建好后再加。
  - 内容聚类编号：对 64 维向量做 k-means，得到一个粗粒度类别。
  - 作者层的视频数和作者首次出现的周。
- 旧 VK 项目里，物品塔最终只有 ID 向量。加过但没转正的有：作者和内容（−37）、候选热度与新鲜度（+10/+17/+8）、候选观看质量（+2/+17/+16）。
7. **在哪跑**
   - 本地：写代码，用约 2,000 个用户跑通，验证结果对得上。
   - 服务器：先租 1 小时测速度，再按实测速度估算总 GPU 小时，Eddy 批准后才正式训练。预算由 Eddy 定。
